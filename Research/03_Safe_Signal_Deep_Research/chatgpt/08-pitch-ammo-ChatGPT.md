## TL;DR — use first
1. Opening: **$15.9B** reported U.S. fraud losses in 2025 (FTC), then show a realistic incoming bank/parcel text.
2. Position against **Scam Shield + Pixel** honestly: protection exists, but your contribution is the *consented next-action and recovery workflow*.
3. In 90 seconds, demonstrate Nemotron planning, a URL lookup, a mocked CAMARA signal, an explicit simulated transfer hold and an evidence receipt.
4. Show the security story: attacker-injected scam text cannot override tools, API keys or user approval.
5. Judges should see a measured synthetic benchmark and one explicit limitation slide, not fabricated accuracy or carrier integration.

## F. Slide structure and 25-second pitch script

1. **Problem** — FTC 2025 reported $15.9B losses (footnoted). T-Mobile already blocks huge traffic, yet customer decision-making remains hard.
2. **Why different** — before/during/after interventions; not a classifier, an approved action workflow.
3. **Live demo** — Nemotron -> URL evidence -> mock telco -> confirm simulated hold -> recovery.
4. **Safety/privacy** — synthetic-only, masked data, approval gate, prompt-injection resistance.
5. **Evidence and future** — real measured test, false positives, honest limits; future real carrier/bank adapters only through authorized partnerships.

> “ScamShield blocks suspicious communications, but a convincing request can still make someone send money. Safe Signal uses Nemotron to investigate the evidence, recommend a safer next step, and—only with permission—take a protective action. Watch a fake bank alert trigger a URL check, a simulated telecom risk signal and a user-approved payment hold. Afterward, we generate a clear recovery path. That's protection before, during and after, not another chatbot that says ‘scam.’”

## G. Hard questions judges might ask

- **“Why T-Mobile if Google Pixel already detects scams?”** Because device warning is strong but different from an authorized carrier-service + payment-verification + customer recovery *workflow*; don't deny existing features. [Google Pixel official](https://store.google.com/intl/en/ideas/articles/pixel-safety-features), [T-Mobile Scam Shield](https://www.t-mobile.com/benefits/scam-shield).
- **“Are you connected to real network and banking APIs?”** No. CAMARA schema-backed operator signals and bank hold are explicitly simulated; live reputation check is real only if executed against an authenticated provider. [CAMARA](https://camaraproject.org/resources), [Nessie](https://api.reimaginebanking.com/).
- **“What's your detection accuracy?”** Show measured true/false positives and per-type recall on a synthetic holdout. Don't infer production accuracy. [Calibration evaluation guidance](https://scikit-learn.org/stable/modules/calibration.html).
- **“What if the message tells Nemotron to transfer money?”** Untrusted text can produce risk *evidence*, never authority; deterministic allowlist and user consent prevent unauthorized side effects. [CaMeL](https://arxiv.org/html/2503.18813).
- **“What data leave the device?”** Exactly the minimized redacted synthetic input sent to the NVIDIA cloud API in this prototype; nothing is falsely marketed as completely local. [NVIDIA API](https://docs.api.nvidia.com/).
